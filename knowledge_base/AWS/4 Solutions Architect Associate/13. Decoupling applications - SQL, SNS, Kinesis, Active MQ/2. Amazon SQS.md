At the core of SQS is a queue, because SQS is a **Simple Queuing Service**

SQS queue is going to contain messages

To contain messages, while something needs to send messages to the SQS queue. Whatever sends messages into the SQS queue is called a **producer**.

It's possible to have multiple producers sending messages to same SQS queue

The message could be whatever we want – process this order or video etc
Whatever message we create goes into the queue.

Then something needs to process the messages from the queue and receive them. They are called **consumers**.

Consumers poll the messages from the queue. They ask the SQS queue, if it has any messages for me. If queue has, it sends the message and then with that message, consumer will process it and delete the message back from the queue

So queuing service is here to be a **buffer** to decouple between producers and consumers

## SQS – Standard Queue
- Oldest offering (over 10 years old)
- Fully managed service, used to **decouple applications**
- Attributes:
	- Unlimited **throughput**
		- Can send as many messages per second we want into the queue
	- Unlimited number of messages
		- Queue can have as many messages we want in the queue
	- Each message is short lived
		- Default retention of messages - 4 days, maximum of 14 days
		- As soon as we send a message to the queue, it has to be read by any of the consumer and deleted by consumer from the queue after being processing, within the retention period
	- Low latency (<10ms on publish and receive)
		- Whenever we send a message or read a message from SQS, we get response within 10 ms on publish and receive
	- Limitation of < 1024 KB per message sent
- Can have **duplicate messages** (at least once delivery, occasionally)
	- Sometimes a message can be delivered twice
	- At least once delivery
	- Need to consider duplicate message possibility, thus need to consider idempotence.
- Can also have **out of the order messages**
	- It's best effort ordering
	- There's another type of offering from SQS dealing with this limitation

## SQS – Producing Messages
- Messages are sent into SQS by producers using SDK (SendMessage API)
- The message is persisted in SQS until a consumer reads and deletes it signifying it's processed
- Message retention:
	- default 4 days, up to 14 days
- Example
	- send an order to be processed as a message containing
		- Order id
		- customer id
		- any attributes we want
- SQS standard has **unlimited throughput**

## SQS – Consuming Messages
- Consumers are applications that we have to write with some code
- These applications can be running on 
	- EC2 instances
	- or on-premises servers if we wanted
	- or AWS Lambda
- SQS queue has a consumer
- Consumer polls SQS for messages
	- Consumer may receive up to **10 messages at a time**
- Consumer's responsibility to process the messages
	- e.g. insert message into RDS database
- Then, since the messages have been received and processed by a consumer, it is consumer's responsibility to go ahead and delete these messages from the queue using the DeleteMessage API
- This DeleteMessage API will guarantee that no other consumer will receive this message going further
- **Purge queue** - we can purge SQS queue which will delete all messages in the queue (helpful while development)

## SQS – Multiple EC2 Consumers (Scaling)
- Multiple EC2 consumers receive and process messages in parallel
- Each consumer will receive a **different set of messages** by calling poll function
- If somehow a message is not processed fast enough by consumer, it will be received by other consumers
- Thus, we have 
	- at least once delivery
	- and best-effort message ordering
- Consumers delete messages after processing them or else other consumers would read it again
- With SQS queues, to increase/improve **processing throughputs**, to have more messages, we can add consumers and do **horizontal scaling**

### SQS with Auto Scaling Group (ASG)
![[Pasted image 20260531092826.png]]
This is a perfect use-case to use **SQS with Auto-Scaling groups**
This is a very common integration will see in exam.
- Consumers will be running on EC2 instances inside of an auto scaling group
- Each one will be polling from SQS queue
- Now, **ASG should scaling on some kind of metric**
	- A metric available to us is the **queue length**
	- CloudWatch metric – Queue Length called **ApproximateNumberOfMessages** is available on any SQS queue
- We can set an alarm
	- Whenever queue length goes over a certain level, then please set up a CloudWatch alarm
	- This alarm should increase capacity of Auto Scaling Group by X amount
	- This will guarantee that once we have more messages in our SQS queue, maybe because there's a surge of orders on our websites, the more EC2 instances will be provided by the ASG and will accordingly process messages at higher throughput

## SQS to decouple between application tiers

Consider an application for processing videos
![[Pasted image 20260531094550.png]]

We could have just one big application (can call it frontend) that takes the request and whenever a video needs to be processed, it will do processing and then insert into an S3 bucket

The problem is that processing may be very long to do and it may slow down website or frontend tier.

So instead, we can decouple application tier and say, request of processing a file and the actual processing of a file can happen in two different applications
Thus, whenever a request to process a file is received, we will send a message to an SQS queue. 
The request to process that file will be in SQS queue and we can create a second processing tier called backend processing application (video processing) in it's own auto-scaling group 
- to receive these messages
- process these videos
- and automatically insert them into S3 bucket

Thus, we can scale frontend and backend accordingly but **independently**
And because SQS queue has unlimited throughputs and unlimited number of messages, it is safe and this is a robust and scalable type of architecture

For frontend, we can use optimal type of EC2 instances or architecture for frontend and different optimal EC2 type or architecture for the backed specifically for video processing like EC2 instances with GPU

## SQS Security
- **Encryption**:
	- In-flight encryption using HTTPS API
	- At-rest encryption using KMS keys (SSE-KMS) or **SSE-SQS** (similar to SSE-S3)
		- for SSE-KMS we have default KMS key of `aws/sqs` like we had for S3 SSE-KMS key called `aws/s3`
	- Client-side encryption if client wants to perform encryption/decryption itself

- **Access controls**
	- IAM policies to regulate access to SQS API

- **SQS Access Policies** (a resource policy)
	- We also have SQS access policies
	- Similar to S3 bucket policies
	- Helpful for cross-account access to SQS queues
	- Useful for allowing other services (SNS, S3, ...) to write to an SQS queue

### Security
#### User based 
- IAM Policies - authorize which API calls should be allowed for a specific user from IAM

#### Resource based
- **Bucket policies** - bucket wide rules from S3 console - allows cross account - **most common** way to do security on S3 bucket
- **Object ACL (Access Control List)** - finer grain (can be disabled)
- **Bucket ACL** - less common

### Note:
an IAM principle can access an S3 object if
- The user IAM permissions **ALLOW** it OR the resource policy **ALLOWS** it
- **AND** there's no explicit **DENY** on the action being performed on the s3 object or bucket

### Encryption:
- Encrypt objects in S3 using encryption keys


### S3 Bucket Policies
- they are JSON based policies
- Resources - buckets and objects
- Effect : Allow or Deny
- Actions: Set of APIs to allow or deny the principal
- Principal: The account or user to apply the policy to
```json
{
	"Version": "2012-10-17",
	"Statement": [
		{
			"Sid": "PublicRead",
			"Effect": "Allow",
			"Principal": "*",
			"Action": ["s3:GetObject"],
			"Resource": ["arn:aws:s3:::examplebucket/*"]
		}
	]
}
```
- Use s3 bucket policy to:
	- Grant public access to bucket
	- Force objects to be encrypted at upload
	- Grant access to another account (Cross account)

### Example bucket policy:
Public Access -> 
```json
{
	"Version": "2012-10-17",
	"Statement": [
		{
			"Sid": "PublicRead",
			"Effect": "Allow",
			"Principal": "*",
			"Action": ["s3:GetObject"],
			"Resource": ["arn:aws:s3:::examplebucket/*"]
		}
	]
}
```
For user access -> Use IAM Permissions
For service access (EC2) -> Use IAM Role attached to service resources
For cross account access -> use S3 Bucket policy

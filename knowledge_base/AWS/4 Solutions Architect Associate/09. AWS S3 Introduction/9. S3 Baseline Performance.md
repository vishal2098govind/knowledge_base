- S3 automatically scales to high request rates, latency 100-200 ms
- Application can achieve at least (in a bucket)
	- 3500 PUT/COPY/POST/DELETE requests per second per prefix
	- or 5500 GET/HEAD requests per second per prefix
- There are **no limits** to number of prefixes in a bucket

### Examples to understand per-second-per-prefix:
- object : bucket-name/folder-1/sub-folder-1/file => prefix : folder-1/sub-folder-1
	- thus, prefix = anything other than the object name (file) and the bucket name
	- thus, this means that, for this file in this prefix, we can get 3500 PUTs and 5500 GETs per second for this one prefix
- if we have another object at : bucket-name/folder-1/sub-folder-2/file => prefix: folder-1/sub-folder-2:
	- then, we get 3500 PUTs and 5500 GETs per second for this one prefix
- Thus, if we spread reads across all four (for example) prefixes evenly, we can achieve 22000 requests per second for GET and HEAD

### Optimizing S3 Performance:
- **Multi-part upload:**
	- recommended for files > 100MB
	- must for files > 5GB
	- helps parallelize uploads - speed up transfers
- **S3 Transfer Acceleration:**
	- increase transfer speed for **uploads**
	- by transferring file to an **AWS edge location**
	- which will forward the data to S3 bucket in target region
	- **Edge location**: there are more edge locations than regions, about 200 edge locations today and growing
	- Is compatible with multi-part upload
	- The edge location once receives the data transfers it to the bucket in the region over fast private AWS network
- **S3 Byte-Range Fetches**
	- Parallelize GETs by requesting specific byte range
	- Better resilience in case of failures
	- Can be used to 
		- speed up **downloads**
		- get partial data (head of file)

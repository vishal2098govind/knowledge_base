We can encrypt objects in S3 buckets using one of 4 methods
- SSE - Server-Side Encryption
	- SSE-S3 with Amazon S3-Managed Keys - Enabled by default
		- Encrypts S3 objects using keys handled, managed and owned by AWS
	- SSE-KMS with KMS keys stored in AWS KMS
		- Leverage AWS KMS Service to manage encryption keys
	- SSE-C with customer-provided keys
		- When we want manage our own encryption keys
- Client-Side Encryption


### SSE-S3
- Encryption is using a key
	- handled
	- managed
	- and owned by AWS
- Object is encrypted server-side
- Encryption type is **AES-256**
- Thus, we must set header to `"x-amz-server-side-encryption":"AES256"` to request S3 to encrypt the objects using SSE-S3 mechanism
- SSE-S3 is enabled by default for new buckets and new objects
![[Pasted image 20260530153909.png]]

### SSE-KMS
- Encryption using keys handled and managed by AWS KMS (Key Management Service) 
- KMS advantages: 
	- user control
	- audit key usage using **CloudTrail** (a service that logs everything that happens in AWS)
- Object is encrypted server side 
- Must set header `"x-amz-server-side-encryption": "aws:kms"`
- Thus, now to read a file from S3 bucket, not only we will need access to the object itself, but also to underlying KMS key that was used to encrypt this object
![[Pasted image 20260530154252.png]]

#### SSE-KMS Limitations
- KMS limits
- KMS Key has it's own APIs - When we upload, it calls **GenerateDataKey** KMS API
- When we download, it calls **Decrypt** KMS API
- we will be doing API calls into the KMS service
- Each of these API calls is going to count towards KMS quotas of API calls per second
	- between 5500, 10000, 30000 req/s based on region
- We can request a quota increase using Service Quotas Console
- If we have a very, **very high throughput S3 bucket** and everything is encrypted using KMS keys, we may go into a **throttling** kind of use-case.
![[Pasted image 20260530154643.png]]
### SSE-C
- keys are fully managed by customer outside of AWS
- S3 does not store the encryption key provided, discarded after use
- HTTPS must be used because we transmit a key into S3 as part of HTTP headers for **every request** being made
- To read that file, the user must again provide the key that was used to encrypt that file
![[Pasted image 20260530155159.png]]

### Client Side Encryption
- Easier to implement if we leverage some client library, such as S3 Client-Side encryption library
- Idea with client-side encryption is that the client must encrypt data themselves before sending to S3
- Clients must decrypt data themselves when retrieving from S3
![[Pasted image 20260530155948.png]]

## Encryption in Transit/In flight (SSL/TLS)
- S3 has two endpoints
	- HTTP endpoint - non-encrypted
	- HTTPS endpoint - encryption in flight 
		- (recommended)
		- mandatory for SSE-C
		- most clients would use HTTPS by default
### Forcing Encryption in Transit - `aws:SecureTransport`
- For this we can use a bucket policy to our S3 bucket
- We can **deny any GetObject operation** if the **`aws:SecureTransport`** is set to false
- **`SecureTransport`** is going to be true whenever using HTTPS and false whenever we are not using an encrypted connection
- Thus, any user trying to use HTTP on our bucket is going to be blocked, but users using HTTPS may be allowed

### NOTES
- Editing encryption type of an object will create **new version** if versioning enabled
- While choosing AWS KMS keys, we should always find one default KMS key, the AWS/S3
- It's called the default KMS key for the S3 service
- Using this **default** key is **not going to cost us any money**
- Creating own KMS key will cost some money every month
![[Pasted image 20260530163715.png]]
- **Bucket Key** option:
	- In case of **SSE-KMS**, we have an option of **Bucket Key**
	- This is to reduce the cost by doing less API calls to AWS KMS
	- And so this is enabled by default

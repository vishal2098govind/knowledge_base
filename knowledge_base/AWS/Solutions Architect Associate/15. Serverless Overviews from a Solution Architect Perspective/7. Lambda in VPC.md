## Lambda By Default
- By default, lambda function is launched outside of our VPC we own (in an AWS-owned VPC)
- Therefore, it cannot access resources in our VPC (RDS, ElasticCache, internal ELB...)
- This will work for accessing any public APIs and also DynamoDB
	- because DynamoDB is a public resource on AWS cloud

## Lambda in VPC
- Can specify VPC ID, subnets and security groups
- Lambda will create an ENI in our subnets and access resources inside VPC

## Lambda with RDS

- If lambda functions directly access database, they may open too many connections under high load
- Thus, can launch RDS Proxy to **pool connections**
- RDS Proxy
	- Improve scalability by pooling and sharing DB connections
	- Improve availability by reducing by 66% the failover time and preserving connections
	- Improve security by enforcing IAM authentication and storing credentials in Secrets Manager
- The lambda function must be deployed in VPC, because RDS proxy is never publicly accessible

## Invoking Lambda from within RDS and Aurora
- Allows to process data events from within database
- Supported for RDS for PostgreSQL and Aurora MySQL
- Must allow outbound traffic to lambda
- DB instance must have required permissions to invoke Lambda function (Lambda Resource-based policy and IAM policy)

### RDS Event Notifications
- Data events are different from RDS Event notifications
	- Tells information about DB instance itself
	- we don't have any information about data itself
	- can use RDS event notifications for subscribing for
		- DB instance
		- DB snapshot
		- DB parameter group
		- DB security group
		- RDS proxy
		- Custom Engine Version
	- Near real time events (up to 5 minutes)
	- Send notifications to SNS or subscribe to events using EventBridge
	- From SNS, we can send to SQS queue or Lambda functions

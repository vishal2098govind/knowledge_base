Fully managed, highly available with replication across multiple AZs

NoSQL database - not a relational database - with transaction support

Scales to massive workloads, since database is distributed internally database

Millions of requests per second, trillions of rows, 100s of TB of storage

Fast and consistent in performance - **single-digit millisecond** performance

Integrated with IAM for security, authorization and administration

Low cost and auto-scaling capabilities

No maintenance or patching, always available
**Thus, no need to provision a database, it's already there right away, we just need to go ahead and create a table and say how much capacity we want to put in this table**

We've two kinds of table classes:
- **Standard table class** for frequently accessed data
- **Infrequent Access (IA) table class**

### DynamoDB Basics
- Database already exists, no need to create
- Made of **tables**
- Each table has primary key
	- Must be decided at creation time
- Each table can have infinite number of items (rows)
- Each item has attributes (can be added over time - can be null)
- Maximum size of an item is 400KB
- Data types supported:
	- **Scalar types**
	- **Document types**
	- **Set types**
- Can **rapidly evolve schemas** in DynamoDB

### DynamoDB Read/Write Capacity Modes
- Control how we manage table's capacity i.e. Read/Write throughput
- **Provisioned Mode** (default mode)
	- Specify number of reads/writes per second
	- Need to **plan capacity before hand**
	- Pay for **provisioned** read capacity units (RCU) and write capacity units (WCU)
	- Possibility to add **auto-scaling** mode for RCU and WCU
	- **Use case**
		- **Predictable** load
		- Evolves **smoothly**
		- need cost **saving**
- **On-Demand Mode**
	- Read/Write automatically scale up or down with workload
	- **No capacity planning needed**
	- Pay for what we use, more **expensive** ($)
	-  Use case
		- **Unpredictable** work load
		- Work loads with steep sudden **spikes**

## DynamoDB Accelerator (DAX)
Fully managed, highly available seamless in-memory cache for DynamoDB

Helps solve read congestion by caching

Idea is that if we have lot of reads on our DynamoDB table, we can create a DAX cluster to solve read congestion by caching the data

We can get **microseconds** latency for cached data

No need to change any application logic

Default TTL of 5 minutes

## DynamoDB - Stream Processing
- Ordered stream of item-level modifications in a table
- Use cases:
	- React to changes in real-time (welcome email to users)
	- Real-time usage analytics
	- Insert into derivative tables
	- Implement cross-region replication
	- Invoke AWS Lambda on changes to DynamoDB table
- Two kind of Stream processing available:
	- **DynamoDB Streams**
		- 24 hours of retention
		- Limited no.of consumers
		- Process using Lambda Triggers, or DynamoDB Stream Kinesis adapter
	- **Kinesis Data Stream**
		- Can choose to send all your changes to Kinesis Data Streams
		- One year of retention
		- Much higher no.of consumers
		- More ways to process data
			- Lambda, Kinesis Data Analytics, Data Firehose, AWS Glue Streaming ETL ...

## DynamoDB Global Tables
- Table replicated across multiple regions
- There's a two-way replication across these tables
- Makes DynamoDB table accessible with low latency in multiple regions
- Active-Active replication
- Applications can **READ** and **WRITE** to table in any region
- Must enable DynamoDB streams as a pre-requisite because this is underlying infrastructure to replicate data across regions

### DynamoDB TTL
- Automatically delete items after an expiry timestamp
- Use cases: Reduce stored data by keeping 
	- only current items
	- adhere to regulatory obligations
	- **web session handling**

### DynamoDB Backups for disaster recovery
- Continuous backups using **point-in-time recovery** (PITR)
	- Optionally enabled for last 35 days
	- PITR to any time within backup window
	- Recovery process creates new table
- On demand backups
	- Full backups for long-term retention, until explicitly deleted
	- Doesn't affect performance or latency of DDB table
	- Can be configured and managed in AWS backup (enables cross-region copy)
	- Recovery process creates a new table

### DynamoDB with S3
#### Export to S3
- Can export a DDB table to S3
- Must enable PITR
- We would export DDB table to S3 to do some queries using Amazon Athena Engine
- Works for any point of time in last 35 days
- Doesn't effect read capacity of table
- Perform data analysis on top of DDB
- Retain snapshots for auditing
- ETL on top of S3 data before importing back to DDB
- Export in DDB JSON or ION format

#### Import from S3
- import CSV, DDB JSON or ION format
- Doesn't consume any write capacity
- Creates a new table
- Import errors logged in CW logs

Lambda functions can use DDB as DB for our APIs and we can do CRUD on DDB tables 
Client should be able to invoke these lambda functions in some way
- We can have client **directly** invoke lambda function, but that means the client would need IAM permissions
- We can use **ALB** to have it in between client and lambda function that would expose lambda function as an HTTP endpoint
- **API gateway** - a serverless offering from AWS which allows to create REST apis that are going to be public and accessible for our clients
	- Client talks to REST API from API Gateway
	- API Gateway will then proxy request to lambda function

### Features by API Gateway
- More than just an HTTP endpoint
- Authentication
- Usage plans
- Development stages
- AWS Lambda + API Gateway => No infrastructure to manage
- Support for WebSocket Protocol
- Can do real-time streaming through API gateway in two different ways
- Handle API versioning
- Handle Different environments (dev, test, prod...)
- Handle Security (Authentication and Authorization)
- Create API keys, handle request throttling
- Swagger or Open API import to quickly define APIs and also can export
- Transform and validate requests and responses to ensure invocation are correct
- Generate SDK and API specifications
- Cache API responses

## API Gateway Integrations High Level
### Lambda Function
- Invoke Lambda function
- Most common way and very easy way to expose REST API backed by AWS Lambda to do full serverless application

### HTTP
- Expose any HTTP endpoint in the backend
- Example
	- internal on premise HTTP APi
	- ALB
- Why?
	- Leverage API Gateway for rate limiting features
	- Caching
	- User authentication, API keys, etc
### AWS Service
- Expose any AWS API through API Gateway
	- Start AWS Step function workflow
	- Post a message to SQS directly from an API Gateway API
- Why?
	- Add Authentication
	- deploy publicly
	- Rate control on some AWS services

## API Gateway Endpoint Types
### Edge-Optimized (default): For global clients
- Requests routed through CloudFront Edge Locations
- Improves latency
- API Gateway still lives only on one region
	- But accessible efficiently from every CloudFront Edge locations
### Regional Endpoint
- For clients within same region only of our API Gateway
- Cloud manually combine with CloudFront distribution
	- more control over caching strategies and distribution
### Private Endpoint
- Can only be accessed only from VPC and using an interface VPC endpoint (ENI)
- Can use resource policy to define access

## API Gateway Security
### User Authentication through
- IAM Roles
	- For internal applications
	- like apps running on EC2 instances 
	- **Cognito** (identity for external users – example mobile users)
	- Custom Authorizer lambda function (own logic)
### Custom Domain Name HTTPS Security
- through integration with AWS Certificate Manager (ACM)
- If using Edge-Optimized endpoint type is used in API Gateway, the certificate must be in **us-east-1**
- If using Regional endpoint type is used in API Gateway, the certificate must be in the same region as API Gateway
- Must setup CNAME or A-alias record in Route53 to point to domain and API Gateway

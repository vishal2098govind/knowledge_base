## Local Name Resolution

Local name resolution occurs locally on the end user's machine without contacting any external servers or systems of any kind

In this type of resolution, there are no root servers, TLD servers or any similar infrastructure

This type of resolution operates with a **host table**.
A simple text file consisting of static mappings between addresses and hostnames

Host table is actually predecessor of DNS, it was one of the earliest name systems ever created in computing, back in the 1970s, when the internet (known as Arpanet at that time), was a small friendly community of a few hundred hosts

The host table was the only way of resolving host names
Owners of new hosts would send an email to hosts master at the `sri-nic.arpa` to request an address and a file named `hosts.txt` would be distributed by the network-information-control-center and manually installed on each host to provide a mapping between these names and their corresponding network addresses.

Each machine would load the host table into memory upon booting and consulting it whenever a name needed. No requests, referrals, or servers were involved

Resolution was entirely local and under the direct control of local computer's administrator

Due to the dominant role of the host tables in this entire process, local name resolution is also known as host table name resolution

Hosts table is represented by the hosts file, which can be found under 
- in windows: Windows/System32/Drivers/etc/hosts
- in linux: `~/etc/hosts`
```sh
$ cd /etc
$ /etc cat hosts
##
# Host Database
#
# localhost is used to configure the loopback interface
# when the system is booting.  Do not change this entry.
##
127.0.0.1	localhost
255.255.255.255	broadcasthost
::1             localhost
```
Wild card entries are not supported
So every domain and subdomain would need to be explicitly defined

Host table is replaced by DNS. Even though, it has following use cases:
- Small local networks
- Improve performance: The host file is read before the DNS name resolution kicks off
	- works for websites that have static IP address mapping


## DNS Resolvers
This is a DNS protocol's component that makes resolution possible in the first place

The first server that receives the client's request is the DNS resolver, which sits between the client and the rest of the DNS ecosystem

Upon receiving the request, the resolver first sees if it can answer the request directly, and if not, it assumes the role of the client and takes it upon itself to have the query resolved on behalf of original client, by contacting the root servers and progressing the name resolution process

After receiving the final answer from the requested domain's authoritative name server, the resolver saves the resolved query in it's cache and forwards it to the original client.

In DNS, the roles of client and server are not mutually exclusive. As it is possible for systems to assume either role, as in this case

### How does the DNS resolver know about the root servers?
- root hints file, which is where the root servers are stored
	- can be found from https://root-servers.org
	- i.e. from https://www.internic.net/domain/named.root
- In a small office or home office network, DNS resolver is typically the router or an IP address provided by our ISP
- Using `ipconfig`, we can see the IP address of DNS Resolver, on windows
- On linux, we can use `resolv.conf` file
```sh
$ cat /etc/resolv.conf
#
# macOS Notice
#
# This file is not consulted for DNS hostname resolution, address
# resolution, or the DNS query routing mechanism used by most
# processes on this system.
#
# To view the DNS configuration used by this system, use:
#   scutil --dns
#
# SEE ALSO
#   dns-sd(1), scutil(8)
#
# This file is automatically generated.
#
search openvpn
nameserver 8.8.8.8 # Google's DNS resolver
nameserver 8.8.4.4
```
Most well known DNS resolvers:
- 8.8.8.8
- 8.8.4.4
- Cloudflare's 1.1.1.1
- Quad9 9.9.9.9

Not all DNS Resolvers behave identically
- Some resolvers support EDNS0 (extension to DNS protocol), some resolvers do not
- Many resolvers support negative caching but not all
- Not all resolvers use same method in choosing which name servers to contact. Some use smooth round-trip-time (SRTT), while some choose at random

## DNS Resolution Types
- Iterative Resolution
- Recursive Resolution

### Iterative Resolution
- Client sends DNS query to a server requesting information about a specific domain name
- Queried server looks for requested information in it's own local data, and if it doesn't have the answer there, it returns a referral containing the names and addresses of the name servers closest to the domain name in the request, to allow the resolution process to continue
- The referral returned contains all name servers listed in it's local data, and it's up to the the client to choose which one to query next
- The client must then **iterate** by sending a new request to this referred server, which again will return either an answer or another referral
- The process continues until the correct server is found and an authoritative answer is given
- The queries involved are known as **iterative queries**, while the server responses are known as **referrals**
- In iterative resolution, it's the **client's responsibility** to keep querying servers until the required information is obtained

### Recursive Resolution
- If the server doesn't have the answer, instead of simply replying the client with a referral to point a name server, as in the case of iterative resolution, the server instead assumes the role of the client, and it takes on the responsibility of continuing with the name resolution process by sending a series of iterative requests down the DNS tree, starting from the root until it finds the authoritative answer for the domain name being requested and forwarded to the original client
- In this type of resolution, the original client gets to send only a single query, which eventually returns the information requested
- That query is known as **recursive query**, which cannot be replied with **referrals**
- Instead, **recursive queries** compel the queried server to find the requested information on behalf of the original client
- In recursive resolution, it's the **server's responsibility** to obtain the DNS information requested by the original client.

## Caching
The purpose of caching in computing is to temporarily store previously acquired data so that future requests for that data can be served faster

As soon as a DNS resolver has the authoritative answer, it caches it before forwarding it to the client, which in turn places the resolved data in it's own cache too

Even errors are cached in same way that a successful resolution would have been, called **negative caching**

If the server doesn't have any relevant information in it's cache at all, it will then proceed sending the usual series of iterative requests until it finds the authoritative answer for the requested domain

Caching is so important in DNS that dedicated DNS servers exists with sole purpose of providing caching functionality only, without having any authority over any domains

These servers are known as Cache-only DNS servers. They are often present in many network deployments.

### Why is there a limited time period for which the resolved names remain cached?
- Whether intentional or accidental, changes do take place in configuration of DNS name servers
- Those changes can result in incorrect responses due to cached information that is no longer valid
- The resolve names get cached for a finite amount of time
- The duration for that time frame is determined by a parameter known as time-to-live (TTL)

## Reverse Name Resolution
- Forward resolution - given domain name, we want to know it's IP address
- Reverse resolution - given an IP address, we want to know it's domain name it's mapped to
- it is called reverse DNS (rDNS)
- We need a parallel hierarchical setup of name servers based on IP address that we had based on name
- Reverse resolution DNS has a special domain called `in-addr.arpa`. 
- `in-addr` stands for internet address
- within that domain, is a numerical hierarchy that covers entire IP address space, with 4 levels of numerical subdomains structured so that each ip address has it's own node, and that node contain an entry that corresponds to domain mapped to that address
- examples of domain names of rDNS servers:
	- `69.in-addr.arpa` - Level 1
	- `171.69.in-addr.arpa` - Level 2
	- `250.171.69.in-addr.arpa` - Level 3
	- `35.250.171.69.in-addr.arpa` - Level 4
- The `in-addr.arpa` reverse name resolution hierarchy covers the entire IPv4 address space
![[Pasted image 20260209165005.png]]
```sh
$ dig www.facebook.com # forward lookup
; <<>> DiG 9.10.6 <<>> www.facebook.com
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 2059
;; flags: qr rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 512
;; QUESTION SECTION:
;www.facebook.com.		IN	A

;; ANSWER SECTION:
www.facebook.com.	618	IN	CNAME	star-mini.c10r.facebook.com.
star-mini.c10r.facebook.com. 21	IN	A	57.144.142.1

;; Query time: 51 msec
;; SERVER: 8.8.8.8#53(8.8.8.8)
;; WHEN: Mon Feb 09 16:54:52 IST 2026
;; MSG SIZE  rcvd: 90
```

```
$ dig -x 57.144.142.1 +noall +answer

; <<>> DiG 9.10.6 <<>> -x 57.144.142.1 +noall +answer
;; global options: +cmd
1.142.144.57.in-addr.arpa. 736	IN	PTR	edge-star-mini-shv-02-ccu2.facebook.com.
```
- Organizations are not compelled to put in place reverse entries for their IP addresses, since it is not as much required as forward mapping.

### Use cases for reverse name resolution
- **Troubleshooting**
- **Filtering spam** - used by email servers who look at the IP address of an incoming email, and if no valid domain name is found, the message is blocked
- **Logging software** - enabling not only IP addresses in the log data, but also display the human readable domain names which the IP addresses are mapped to


## Manipulating the order of name lookups
- in Linux systems, we can use `nsswitch.conf`, which stands for name service switch configuration, 
- it is used by GNU-C library to determine the sources from which to obtain name service information for name queries and in what order

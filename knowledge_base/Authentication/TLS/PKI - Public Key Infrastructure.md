### Explanation

#### Concepts:
**Symmetric Encryption**:
Alice and bob need same symmetric key to encrypt data and decrypt data.
Works well with large data.
Algorithms:
- AES
Problem: 
- How both parties get the symmetric key?
- There's no secure way to send the symmetric key to each other
- If there's a secure way to send the symmetric key, then why not use that way to data itself?

**Asymmetric Encryption**:
Alice and bob both generate pair of keys - public and private keys
If data is encrypted using private key, it can only be decrypted using public key
If data is encrypted using public key, it can only be decrypted using private key
When a private key is used to encrypt, it is called **digitally signing**
When a public key is used to decrypt, it is called **verifying**
When a public key is used to encrypt, it is simply called **encrypting**

Asymmetric Encryption is used to solve the problem with Symmetric Encryption of sharing the symmetric key to both the parties.

Algorithms: RSA, Diffie-Hellman

**Hashing**:
Hashing is used mainly for verifying if the data that is received is actually what that was sent - i.e. mainly for data integrity
A hashing function takes in a parameter of any length and always returns hash of same length
Algorithms: SHA-256, MD5
Hashing is not recoverable, i.e. we cannot get back the original data from the hash.
And Hashing is always idempotent i.e. no matter how many times we pass in a data into the hashing function, we always get the same hash.
Thus, mostly Hashing is used to verify data by comparing two hashes. If two hashes are same, then the data underlying the hash is also same.

**CSR**: Certificate Signing Request

**`pub`**: RSA public key
**`pvt`**: RSA private key
**`symm-key`**: Symmetric Key
**`HASH(k)`**: hash function (like SHA-256) taking input parameter `k`
**`Sign(pvt, k)`**: encrypts the input parameter `k` using the `pvt` private key
**`Verify(pub, k)`**: decrypts the input parameter `k` using the `pub` public key
**`ENCP(pub, k)`**: encrypts the input parameter `k` using the `pub` public key
**`DCP(pvt, k)`**: decrypts the input parameter `k` using the `pvt` p

`WS.pub` -> public key of web server
`WS.pvt` -> private key of web server
`BR.symm-key` -> Symmetric key generated by BR
similarly
`ICA.pub`, `ICA.pvt`, `RCA.pub`, `RCA.pvt`

ICA side:
- prepares a RSA key-pair
	- obtains `ICA.pub` and `ICA.pvt`
- sends CSR to RCA:
- in the CSR, passes the ICA.pub along with identification details of the ICA

RCA side:
- receives CSR from ICA
- validates identification of ICA present in the CSR
- prepares hash of the `ICA.pub` i.e. `HASH(ICA.pub)`
- signs the hash of the `ICA.pub` and prepares a digital signature
- let that digital signature be `Sign(RCA.pvt, HASH(ICA.pub))`
- then, it prepares the certificate by bundling the digital signature and the `ICA.pub` together and responds back to ICA. This is called issuing of a certificate.

ICA Side:
- Now, ICA receives a certificate issued by RCA
- i.e. it now has: 
	- `ICA.pub`
	- `Sign(RCA.pvt, HASH(ICA.pub))`

WS Side:
- prepares RSA key-pair
	- obtains `WS.pub` and `WS.pvt`
- sends CSR to ICA:
- in the CSR, passes the `WS.pub` along with identification details of the WS

ICA side:
- receives CSR from WS
- validates identification of WS present in the CSR
- prepares hash of the WS.pub i.e. `HASH(WS.pub)`
- signs the hash of the WS.pub and prepares a digital signature
- let that digital signature be `Sign(ICA.pvt,HASH(WS.pub))`
- then, it prepares the certificate by bundling 
	- the digital signature 
	- and the WS.pub together 
	- and the RCA issued certificate 
- i.e. ICA bundles (also called the chain of trust)
	- `WS.pub`
	- `Sign(ICA.pvt, HASH(WS.pub))`
	- `ICA.pub`
	- `Sign(RCA.pvt, HASH(ICA.pub))`
- and responds back to WS. This is called issuing of a certificate.

WS Side:
- Now, WS receives a certificate issued by ICA
- i.e. it now has: 
	-  `WS.pub`
	- `Sign(ICA.pvt, HASH(WS.pub))`
	- `ICA.pub`
	- `Sign(RCA.pvt, HASH(ICA.pub))`

BR Side:
- When the browser wants to connect with the WS, it sends TLS Client Hello Request

WS Side:
- WS responds with the certificate issued by ICA which has
	-  `WS.pub`
	- `Sign(ICA.pvt, HASH(WS.pub))`
	- `ICA.pub`
	- `Sign(RCA.pvt, HASH(ICA.pub))`

BR Side:
- The browser receives the certificates as a response to the TLS Client Hello it sent before
- the Operating System on which the browser is running must be having RCA.pub
- Browser uses RCA.pub to **verify** the `Sign(RCA.pvt, HASH(ICA.pub))` signature i.e. does `Verify(RCA.pub, Sign(RCA.pvt, HASH(ICA.pub)))`
	- on verifying (i.e. decrypt the `Sign(RCA.pvt, HASH(ICA.pub))` using `RCA.pub`), it obtains the `HASH(ICA.pub)`
	- browser then performs same hash function on the `ICA.pub` it received and matches the two hashes
	- if they match, it trusts the ICA now (chain of trusts)
- it then similarly uses `ICA.pub` to **verify** the `Sign(ICA.pvt, HASH(WS.pub))` i.e. does `Verify(ICA.pub, Sign(ICA.pvt, HASH(WS.pub)))`
- if verified, it trusts the WS now.
- Then, the Browser generates a symmetric key which will be used to encrypt the application data to be sent after the connection is established
- The symmetric key is encrypted using the `WS.pub` since the browser now trusts `WS`.
- Let's say after encrypting the symmetric key it is denoted as `ENCP(WS.pub, BR.symm-key)`
- The browser sends the `ENCP(WS.pub, BR.symm-key)` back to the browser

WS Side:
- Now, the WS received the `ENCP(WS.pub, BR.symm-key)`
- It decrypts it using the `WS.pvt` i.e. does `DCP(WS.pvt, ENCP(WS.pub, BR.symm-key))` and obtains the `BR.symm-key`
- Now, both BR and WS have `BR.symm-key` which they are going to use in the rest of the TLS/TCP session while transmitting application data in the socket
